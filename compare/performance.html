7.3 性能对比与实测 ​

"SVG 和 Canvas 哪个快"是可视化讨论中被问得最多、也被答得最差的问题——绝大多数答案忽略了图元数量与更新频率这两个前提。本页先把三种渲染模式的成本模型讲透，再给出一个可亲手操作的压测组件：同一批漂移的圆点，分别用 SVG 与 Canvas 2D 渲染，切换图元数量，亲眼看两条帧率曲线的不同走势。读完本页，你应当能把任何性能问题翻译成"数量乘频率落在哪段成本曲线上"，并知道如何亲手验证。

帧预算：一切性能讨论的标尺 ​

流畅的含义不是"能动"，而是每一帧都在预算内完成。显示器的刷新率决定了每帧允许的总耗时——JS 执行、样式计算、布局、绘制、合成，全部加在一起。在讨论任何"快与慢"之前，先把这把标尺立起来：

刷新率帧预算约值含义
60Hz16.7ms主流设备基准线，超过即掉帧
90Hz11.1ms部分移动设备
120Hz8.3ms高刷屏，预算直接减半
144Hz6.9ms电竞屏，对主线程要求苛刻

超出一帧预算，浏览器只能跳过这次刷新，画面原地停留一帧——这就是掉帧。偶尔掉一两帧人眼尚可容忍，连续掉帧就成了肉眼可见的卡顿。还要注意两点：预算并不全归你，浏览器自身也要占用其中一部分；单次超过 50ms 的主线程任务会被标记为 long task，是卡顿排查的重点对象。

预算具体花在哪儿？一帧的主线程工作大致分四段：JS 执行（你的更新逻辑）、样式计算与布局（DOM 与 SVG 更新逃不掉的一段）、绘制（把图形光栅化到图层）、合成（图层拼合上屏）。不同渲染模式的差异，本质上就是这四段各自占多少：SVG 更新四段全走，Canvas 2D 只有 JS 与绘制两段，WebGL 把绘制段整体搬到 GPU。带着这张分段图去读后面的成本模型，每条结论都能对号入座。

性能讨论的全部目标可以浓缩为一句话：让你的每帧总耗时，稳定地留在帧预算之内。

顺带纠正一个直觉误区：帧率不是越高越好。超过显示器刷新率的帧是浪费（屏幕根本来不及显示），而真正伤体验的是波动——稳定 30fps 的观感远好于在 45 与 60 之间来回跳。优化的目标函数因此有两个：均值达标，方差够小；后者常常被忽视，却更能解释用户口中的"一顿一顿"。

帧预算管的是渲染，交互响应另有一笔预算：从用户输入到画面给出反馈，整个链路超过约 100ms 就会产生可感知的迟滞。高频交互场景（拖拽、画笔、实时筛选）不能把帧预算全部花在绘制上，要给输入处理与命中检测留出余量——这也是"预算内"的真实含义：不是贴着 16.7ms 花光，而是留出应对波动的缓冲。

成本模型机理分析 ​

性能结论只能从机理推导，不能从印象出发。三种渲染模式每一帧的"账单"完全不同：账单由哪些项目构成、哪一项随数量放大、哪一项是固定开销，决定了它们各自的数量级天花板。下面逐一拆解，所有结论都可以在前一页的帧预算分段图里对号入座。

SVG：每次更新都是一次 DOM 操作 ​

SVG 是保留模式：每个图形都是 DOM 树中的真实节点。对一个 circle 改一次 transform 属性，浏览器实际执行的工作是：

  1. 属性写入：JS 调用 setAttribute，修改节点的属性值；
  2. 样式失效：浏览器标记该节点及其子树的样式结果失效，下一帧样式计算阶段重新求值；
  3. 重排与重绘：几何属性变化触发图形子树的布局重算，再把受影响区域重新光栅化、合成上屏。

单个节点的单次更新成本以微秒计，完全可以接受；问题在于它乘以节点数。一千个节点每帧各改一次属性，就是一千次属性写加一整棵子树的样式失效与重绘——DOM 操作本身不慢，慢的是"每帧乘以一千"。节点数上千之后，仅属性写入与样式计算就可能吃掉大半个帧预算，重绘区域再一叠加，掉帧不可避免。

更要留意的是，SVG 的这笔账与"你改了多少"关系不大：哪怕只移动一半节点，样式计算与绘制管线的固定开销仍然存在。这就是保留模式的成本特征——省心，但不便宜。工程上的应对只有两条路：减少节点数（合批、抽稀、Canvas 混排），或降低更新频率（节流、按需刷新），治本的方式始终是换渲染模式。

SVG 动画的写法也会显著影响账单，对比两种常见写法：

js
// 反例：每帧重建整段 SVG 字符串——节点销毁重建，成本最高
function frameBad() {
  svg.innerHTML = dots.map((d) => '<circle cx="' + d.x + '" cy="' + d.y + '" r="4"></circle>').join('')
}

// 正解：节点只建一次并缓存引用，每帧只写 transform 属性
function frameGood() {
  for (let i = 0; i < dots.length; i++) {
    circles[i].setAttribute('transform', 'translate(' + dots[i].x + ' ' + dots[i].y + ')')
  }
}

正解已经是 SVG 动画的最小必要工作——本页压测组件用的正是它。也就是说，组件里 SVG 模式的掉帧是"最佳写法下"的掉帧，是渲染模式本身的天花板，而不是写法粗糙造成的。

Canvas 2D：每帧全量重绘，成本约等于指令数 ​

Canvas 是立即模式：没有节点，没有样式失效，没有重排。每帧的成本结构简单得多——clearRect 清屏，然后把全部图元重新画一遍，总成本约等于绘制指令数乘以单条指令的 CPU 成本。

这个模型有两个直接推论：

  • 成本与图元数严格线性，没有隐藏的固定开销，也没有节点管理的额外支出，所以曲线平缓、可预测；
  • 单条指令的成本差异很大，同样是"一万个图元"，画一万个矩形与画一万条贝塞尔曲线，成本可以差出数倍。

常见指令的成本分级大致如下（相对量级，因浏览器实现而异）：

成本档位典型指令每帧可用量级参考
便宜fillRect、clearRect、小图 drawImage万级无压力
中等arc、短路径 lineTo、短文本 fillText数千级可用
昂贵复杂 path、渐变、阴影、大范围缩放 drawImage数百级即需谨慎

Canvas 模式的省钱空间完全在工程手段上：离屏缓存把复杂图元压缩成一次位图拷贝、脏矩形只重绘变化区域、分层画布隔离动静、避免每帧分配对象——这套"性能四板斧"在 Canvas 动画与性能优化 一章有完整展开。

还有一个常被忽略的成本乘数：高分屏。DPR 为 2 的屏幕上，画布位图像素是 CSS 像素的四倍，fillRect 之外的每条指令都在为四倍像素付费；DPR 为 3 的移动设备则是九倍。同样一万个圆点，在 1x 屏与 3x 屏上的绘制耗时可以差出数倍——这正是"同一页面不同设备掉帧点不同"的主要来源之一，也是压测必须在目标设备上做的又一个理由。

WebGL：GPU 并行光栅，数量级的吞吐 ​

WebGL 把渲染搬上 GPU：顶点数据一次性提交到显存，着色器程序以大规模并行的方式完成光栅化。CPU 每帧的工作只剩更新少量 uniform 与发起绘制调用，成千上万个顶点的变换与着色在 GPU 上并行完成。

这带来了数量级的吞吐：十万级图元仍能保持流畅，前提是数据组织得当（合批绘制、实例化渲染）。代价同样醒目：

  • 编程模型复杂：缓冲管理、着色器、矩阵变换，调试工具链薄弱；
  • 状态切换昂贵：频繁切换纹理、着色器程序与缓冲会迅速吃掉 GPU 的红利，draw call 次数本身成为新瓶颈；
  • 文本与 UI 是弱项，需要额外的位图字体或 HTML 浮层方案。

Three.js 等引擎的价值，正是把这套复杂模型包装成场景图，让多数业务代码不必直面 GPU，同时把合批与状态排序这些优化内建在渲染器里。换句话说：WebGL 的吞吐上限极高，但"裸写"与"写好"之间隔着一整套引擎工程——这也是 3D 需求几乎必然经由引擎而非原生 API 落地的原因。

典型量级经验 ​

综合机理与常见工程经验，"每帧全量更新仍能保持流畅"的动态图元量级大致如下。所谓"动态图元"，指每一帧都要重新计算并重新呈现的图形元素；静止的背景、坐标轴不在此列——这也是为什么真实图表能承载的数据量，常常比"全量动画图元"的上限乐观。

渲染模式每帧更新仍流畅的动态图元量级量级背后的原因
SVG数百到一千节点级 DOM 开销与样式重算随数量陡增
Canvas 2D数千到数万成本线性于指令数，无固定节点开销
WebGL数万到数十万GPU 并行光栅，瓶颈在数据组织而非数量本身

表中没有列 DOM 与 CSS：它的甜区是数十个图元，且大多用于"偶尔更新"的仪表盘而非每帧动画；一旦进入每帧更新的领域，重排成本会让它在三位数节点时就败下阵来，因此不参与这张表的比较。

一个使用技巧：把表中的量级当作"预警线"而不是"合格线"——评估需求时，只要预计图元数达到某模式上限的一半，就该触发原型验证；等到贴着上限才发现掉帧，返工成本最高。反过来，远低于下限时也不必为"未来的性能"过度设计，量级表同样能告诉你什么时候可以安心选择开发效率更高的方案。

三点必须强调：

  • 这是量级经验而非精确分数线，具体数字因设备性能、浏览器实现、绘制内容（圆点与复杂路径完全不同）、是否高分屏而异，同一页面在不同机器上的掉帧点可以相差数倍；
  • 表中"流畅"指接近显示器刷新率的稳定帧率（60Hz 屏幕即约 60fps），不是"还能动"；
  • 任何涉及性能的技术决策，都应在你自己的目标设备与目标浏览器上实测，本文任何表格都不能替代实测。

上层库的性能画像 ​

五大技术里有三位的性能不直接等于其渲染模式，值得单独说明——它们各自的优化手段，恰好是"库在信息优势上做文章"的三个范例。

Fabric.js：底层是 Canvas 2D，对象变化后默认全量重绘，因此继承 Canvas 的线性成本曲线；但每个对象还附带选中框、控制点与状态管理的额外开销，同等图元数下比裸 Canvas 更贵。它的甜区是数百个可交互对象——这也是编辑器类产品的真实规模，在这个区间里交互流畅度完全够用。

ECharts：同样是 Canvas 渲染，但图表库手里有信息优势——它知道数据的语义。数据缩放时的抽样、大数据量的渐进式渲染（分批绘制避免长帧）、按量级自动降级这些手段内建在库里，让它在十万级数据点上仍能交付可用帧率；代价是极端定制时这些优化可能帮不上忙。它可选的 SVG 渲染器则适合小数据量加高交互加矢量导出的场景。

Three.js：GPU 吞吐巨大，但帧率表现取决于场景组织而非图元总数：实例化渲染（InstancedMesh）合并同类物体、静态几何合批、控制灯光与阴影数量、减少每帧的材质与程序切换，这些是 3D 场景的性能基本功；做不到位，几十个模型的场景照样掉帧。

三位的共同教训是：库改变不了渲染模式的物理特性，只能在信息优势上做文章。Fabric.js 管对象、ECharts 懂语义、Three.js 组织场景——各自省下的钱，都来自它比裸 API"多知道"的那一部分。选库时问一句"它比我多知道什么"，比问"它快不快"更接近本质。

更新频率：与数量同样重要的变量 ​

数量决定单帧成本，频率决定这笔成本多久支付一次。四个降频手段经常比换技术更有效：

  • 按需渲染：数据没变就不重绘。ECharts 与 Fabric.js 默认就是这种模式，手写 Canvas 时应同样遵守——静态页面还在 60fps 空转，是最常见的性能浪费；
  • 更新节流：高频数据流（行情、传感器）按固定节奏批量应用，例如每 100ms 合并一次再渲染，人眼分辨不出差别，帧预算立刻宽裕；
  • 动静分层：背景、网格、坐标轴这类静态内容画在离屏层反复贴用，每帧只重绘真正变化的部分，这是图表库处理大数据量的标准结构；
  • 离屏休眠：标签页切后台时 rAF 会自动暂停，但可视区外的图表实例仍在白跑——用 IntersectionObserver 把滚出视口的动画停掉，长页面常常躺着十几个看不到的动画实例。

把"数量乘以频率"控制在预算内，常常能让原本"必须上 Canvas"的需求继续留在 SVG 的舒适区——选型结论也因此可能改变，这正是把频率纳入评估的意义。

把机理用起来：两个推演实例 ​

实例一：组织架构图，200 个节点，仅拖拽操作时局部更新。 数量在 SVG 甜区内，更新低频，交互需求深（每个节点可点、可 hover、要显示姓名文本）。结论：SVG 轻松胜任，Canvas 反而要自建命中检测与文本排版——数量与频率都低时，保留模式的便利是净收益。

实例二：直播间点赞特效，峰值每秒新增上千个粒子，单个粒子存活约两秒。 常驻图元数千到上万，每帧全量更新，完全没有图元级交互。结论：Canvas 2D 是正解；若还要叠加复杂形变与光晕，或峰值再涨一个量级，直接上 WebGL 方案。SVG 在这个数量乘频率下会稳定掉帧，与写法优劣无关。工程上还要补一条：粒子的生命周期管理用对象池（死亡粒子的内存直接复用），避免每秒上千次的对象创建把 GC 抖动引入帧率曲线。

两个实例用同一张量级表、同一套成本模型，结论却完全相反——这正是"先定位、再比较"的含义。

正确的测试方法论 ​

帧率测试极易得出错误结论，方法比工具更重要。七条基本原则：

控制变量。 两种方案必须渲染同一批状态：同样的运动轨迹、同样的舞台尺寸、同样的颜色与形状。任何一边多做一点事，比较就失去意义——本页压测组件让两种模式共享同一份粒子状态数组，原因正在于此。业务压测同理：对比两个图表库时，喂给它们的数据集、画布尺寸、更新频率必须逐项对齐，否则你测的是两个不同的问题。

测帧时间，不只测帧率。 FPS 是帧时间的倒数，会掩盖分布信息：平均 55fps 可能是"全部 18ms"，也可能是"一半 10ms 一半 26ms"，后者体感明显更卡。严肃测试应记录每帧耗时，关注长帧与 long task，而不只盯平均值。

用 performance.now 手动采样。 在帧回调里记录相邻两帧的时间差，用最近几十帧的滑动平均得到稳定读数。标准写法如下：

js
// 帧率采样：环形缓冲最近 30 帧的帧时间，滑动平均后取倒数
const FT_N = 30
const buf = new Float32Array(FT_N)
let idx = 0
let count = 0
let sum = 0
let last = performance.now()

function frame(now) {
  const raw = now - last // 本帧距上帧的真实毫秒数
  last = now
  if (count < FT_N) {
    sum += raw
  } else {
    sum -= buf[idx] // 缓冲已满：先减去被覆盖的最旧样本
    sum += raw
  }
  buf[idx] = raw
  idx = (idx + 1) % FT_N
  count = Math.min(count + 1, FT_N)

  const fps = 1000 / (sum / count) // 滑动平均帧率
  // …此处是渲染逻辑…
  requestAnimationFrame(frame)
}
requestAnimationFrame(frame)

为什么不用 setInterval 定时读数？因为 rAF 回调本身就是与刷新对齐的时钟，相邻回调的间隔就是最真实的帧时间；定时器与渲染管线不同步，测出的只是定时器的调度抖动。采样点必须长在渲染循环内部，这是帧率测量的第一原则。

避开干扰源。 关闭 DevTools 再测（打开时渲染与 JS 都有额外开销）；页面切到后台时 rAF 暂停，读数无意义；刚加载的页面 JIT 尚未热身，前几秒的读数偏低，应丢弃不看。

在目标设备上测。 开发机的性能通常是用户机器的两到四倍，低端安卓与老旧办公机才是性能决策的真正依据。DevTools 的 CPU 节流（throttling）可以粗略模拟，但不能替代真机。

移动端是另一个世界。 桌面端的流畅不代表移动端可用：移动 GPU 更弱、内存更紧，且存在热节流——机身发热后芯片降频，长时间运行的页面会越来越慢。移动端压测要连续跑满几分钟，观察帧率是否随温度上升而下滑，短时测试测不出热节流。

需要定位"慢在哪一环节"时，再打开 Performance 面板录制一段：火焰图会清楚显示耗时在 JS 执行、样式计算、绘制还是合成。录制的正确姿势是短时多次——录三到五秒、重复几次看稳定模式，而不是录一分钟然后在噪声里大海捞针。

最后，记录实验条件。设备型号、浏览器版本、是否高分屏、页面缩放比例、电量模式（省电模式会限制性能）都会改变结果。一份不写条件的性能报告，结论再漂亮也无法复现；把条件写进报告，是让结论可讨论、可传承的最低成本。

当实测结果与预期不符时 ​

实测偶尔会给出与成本模型矛盾的读数，排查按以下顺序进行：

  • 先查写法：SVG 侧是否每帧重建了节点，Canvas 侧是否每帧创建了渐变等昂贵对象、是否误开了阴影——写法问题远比模式问题常见；
  • 再查环境：是否开着 DevTools、是否插着电源（省电模式限频）、是否视频会议正在抢 GPU、页面是否被嵌在 iframe 里叠加了额外合成层；
  • 查硬件加速：浏览器的 GPU 加速可能因驱动黑名单被禁用，此时 Canvas 与 WebGL 会退回软件渲染，读数异常偏低，chrome 系浏览器可在 GPU 状态页确认；
  • 最后才怀疑结论：个别浏览器对特定指令有针对性优化或劣化，单一数据点不改变量级规律，多换两台设备再下判断。

走完这四步仍解释不了的异常，才是值得写进团队知识库的新发现——带着你的实验条件、火焰图与最小复现去社区求证，这时的你已经在为公共知识做贡献了。

建议的操作顺序，能让观察更干净：

  1. 每切一档数量，等两到三秒再看读数——滑动平均需要时间稳定，刚切换的瞬间还混着建造与 JIT 的扰动；
  2. 两种模式各测一轮后，回到各自掉帧的档位停留十秒，观察帧率是稳定还是缓慢下滑——缓慢下滑往往意味着热节流或内存压力开始介入；
  3. 有条件的话，把同一页面发到手机上重做一遍，移动端的两条曲线分岔通常更早、更陡。

组件的设计逻辑 ​

这个组件的全部设计都服从一个目标：让两种模式各自做最小必要工作，从而公平地暴露成本模型差异。

  • 共享同一份粒子状态：位置、速度、半径、颜色存在一个预分配的数组里，物理更新对两种模式完全相同，渲染是唯一的变量；
  • SVG 每帧只更新 transform：circle 节点在挂载时用字符串拼 innerHTML 一次性批量建好（建造成本只发生一次，不混入每帧测量），之后每帧只对每个节点写一次 transform 属性——这是真实 SVG 动画的最小必要工作，属性写、样式失效与重绘的成本由浏览器买单；
  • Canvas 每帧全量重绘：clearRect 清屏后把全部圆点重画一遍——立即模式没有增量可言，这就是 Canvas 的最小必要工作；
  • 帧率读数诚实：最近 30 帧的帧时间滑动平均，直接写 DOM 文本显示，不走框架响应式，避免测量行为本身干扰测量结果；
  • 粒子运动刻意缓慢：速度低到肉眼刚好能察觉漂移，让"渲染开销"成为帧率的唯一决定因素，而不是运动复杂度；
  • 数量切换只改可见范围：全部粒子预分配一次，切换数量不触发任何对象创建，GC 不会混入测量；
  • SVG 用 innerHTML 一次性建造：批量字符串拼接只发生一次，避免了逐节点 createElementNS 的建造成本——建造与运行两笔账分开，每帧测到的才是纯更新成本。

结果解读指引 ​

预期会观察到的现象（再次强调：关注的是趋势而非精确分数——你的具体数字几乎必然与下表描述不同，但曲线的相对形状大概率一致）：

观察到的现象说明了什么
两种模式 500 档都接近满帧小规模下成本模型差异不显现，选谁都行
SVG 从 2000 到 5000 档明显掉帧节点级 DOM 开销开始吞噬帧预算
Canvas 到 5000 甚至 10000 档才下滑指令模型的线性成本更平缓
高档位下 SVG 帧率先降后稳在低值每帧成本稳定超过预算，进入新的平衡
同档数字与同事机器明显不同掉帧点因设备而异，结论必须实测
打开 DevTools 后全体掉帧测量环境本身引入开销，应关闭再测

把观察结论翻译回工程语言：图元数量与更新频率的乘积，决定你应该站在成本曲线的哪一段上。 偶尔更新一千个节点，SVG 毫无压力；每帧更新一万个图元，Canvas 2D 才刚开始热身；再往上一个量级，就该轮到 WebGL 登场了。

最后提醒一句组件的边界：它测的是"小圆点每帧全量更新"这一种负载。真实业务的绘制内容更复杂（路径、文本、图片），各自的掉帧点会相应前移，但两条曲线的相对形状不变——请把这个组件当作心智模型的验证器，而不是你的业务的模拟器。

小结 ​

三种渲染模式的成本模型各不相同：SVG 的每次更新是节点级 DOM 操作，账单随节点数陡增；Canvas 2D 每帧全量重绘，成本线性于绘制指令数；WebGL 把光栅化交给 GPU 并行完成，用编程模型的复杂度换数量级的吞吐。典型量级上，SVG 适合数百到一千的动态图元，Canvas 2D 覆盖数千到数万，WebGL 可达数十万——但这只是量级经验，任何严肃决策都应在目标设备上实测。压测组件的价值在于展示两条帧率曲线的形状差异：趋势是普适的，数字是因机而异的。下一页开发成本与选型决策把性能结论与开发成本合并，给出可直接执行的选型流程。
