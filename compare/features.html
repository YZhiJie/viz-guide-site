7.2 核心特性横向对比 ​

上一页用二维地图解决了"技术之间是什么关系"，本页回答"每项技术具体强在哪、弱在哪"。一张十一行的特性矩阵把五大技术摆到同一标尺下，随后每个技术一小节的优缺点清单给出诚实的使用建议——包括什么时候不要用它们。读完整页你应当能回答两类问题：某特性"谁有谁没有"（矩阵的职责），以及某场景"该用谁不该用谁"（优缺点清单的职责）。

关于体积量级的四点说明 ​

  • 表中均为压缩后（minify）的保守量级，gzip 后大致降至三分之一上下：Fabric.js 约百 KB 级，ECharts 完整包约三百 KB 级，Three.js 约两百 KB 级；传输层之外还有解压与解析成本，低端机上不可忽略；
  • ECharts 支持按需引入（只打包用到的图表与组件），Three.js 支持 tree-shaking，两者的实际增量大头取决于你引用了多少功能；Fabric.js 的模块化程度相对有限，通常是整体引入；
  • 体积只是成本的一项：零依赖的 SVG 在大数据量下付出的运行时成本，可能远高于引入一个优化良好的库。体积、运行时性能、开发效率是三本独立的账，要分开算；
  • 还有第四笔隐性成本：占用的不只是带宽，还有主线程。库的解析与初始化发生在页面加载的关键路径上，低端机上数百 KB 级 JS 的解析耗时是可感知的；按需引入与路由级懒加载不只是省流量，也是在缩短白屏时间。

五种代码形态速览 ​

矩阵给出的是"有没有"，代码形态给出的是"写起来像什么"。同样画一个蓝色矩形，五种技术的风格差异一眼可辨——注意每段代码里"状态住在哪"，这是理解后续所有优缺点的前提。

Canvas 2D——指令式，状态全在自己手里：

js
// 先拿画笔，再逐条下令；画完浏览器就忘记这个矩形
const ctx = canvas.getContext('2d')
ctx.fillStyle = '#2f7ae5'
ctx.fillRect(20, 40, 120, 160)

SVG——声明式，样式可以全部交给 CSS：

html
<!-- 矩形是文档中的真实节点，可用 CSS 与事件直达 -->
<svg viewBox="0 0 200 240">
  <rect x="20" y="40" width="120" height="160" fill="#2f7ae5"></rect>
</svg>

Fabric.js——对象式，交互能力随对象附赠：

js
// new 一个对象放进画布，选中、拖拽、缩放、序列化自动获得
const rect = new fabric.Rect({
  left: 20,
  top: 40,
  width: 120,
  height: 160,
  fill: '#2f7ae5'
})
canvas.add(rect)

ECharts——配置式，只声明要什么：

js
// 数据与映射声明完，坐标系、刻度、提示框、动画全部自动
chart.setOption({
  xAxis: { type: 'category', data: ['一月', '二月', '三月'] },
  yAxis: { type: 'value' },
  series: [{ type: 'bar', data: [86, 120, 240] }]
})

Three.js——场景式，搭建一个世界：

js
// 几何体加材质组成网格，放进场景，交给相机与渲染器
const mesh = new THREE.Mesh(
  new THREE.BoxGeometry(1, 1, 1),
  new THREE.MeshStandardMaterial({ color: '#2f7ae5' })
)
scene.add(mesh)

从指令到声明、从对象到场景，五段代码浓缩了抽象层级的整条光谱。读这些片段时建议顺手记住各自的"心智触发词"：看到 getContext 就知道状态全归自己，看到 XML 节点就知道 CSS 与事件可用，看到 new 对象就知道序列化现成，看到 setOption 就知道定制边界在配置项里，看到 scene 就知道性能取决于场景组织——触发词比 API 细节更能帮你在评审现场快速反应。接下来逐技术给出诚实的优缺点清单。

Canvas 2D：自由的位图 ​

优点

  • 零依赖、零加载成本，API 二十余年高度稳定，几乎不存在升级包袱；
  • 指令级控制，没有任何框架约定挡在你和像素之间；
  • 图元数量上限比 DOM 与 SVG 高一到两个量级，万级动态图元可用；
  • 与 ImageData 结合可做逐像素处理，这是其他方案无法替代的能力。

缺点

  • 没有对象模型，图元不可寻址，交互、动画、状态管理全部自建；
  • 文本只有 fillText 级别的能力，复杂排版要自量宽、自换行；
  • 无障碍缺失，屏幕阅读器无法感知画布内容；
  • 高分辨率屏幕要手动处理 DPR，否则线条发虚。

最适合：粒子特效、大量动态图元的实时场景、像素级图像处理、轻量小游戏、自定义程度极高的图表渲染层。

不适合：需要图元级交互与无障碍的常规图表、以文本为主的排版场景、需要矢量导出的场合。

SVG：文档化的矢量图形 ​

优点

  • 矢量本质，任意缩放与打印都清晰，viewBox 让响应式几乎免费；
  • CSS 全面接管样式、过渡与动画，与现有前端工程体系无缝衔接；
  • 事件直达每个图元，交互实现成本最低；
  • 文本是真实文本：可选中、可搜索、可翻译、对屏幕阅读器友好；
  • 可整体序列化为文本，天然适合服务端生成与静态站点。

缺点

  • 节点数量存在实际上限，上千之后每次更新都要惊动样式与绘制管线；
  • 复杂滤镜与大面积渐变的渲染成本不低；
  • 属性体系庞杂，viewBox、preserveAspectRatio、变换原点等概念需要专门学习；
  • 对大数据量与高频更新场景无能为力。

最适合：图标与插画、中等数据量的交互图表、需要无限缩放与打印的矢量图、以图形为主的内容型页面。

不适合：高频更新的动态场景、数千以上图元的可视化、逐像素效果。

Fabric.js：画布上的对象模型 ​

优点

  • 现成的编辑器交互：选中、八向控制点、拖拽、缩放、旋转、成组，开箱即用；
  • 场景可整体序列化为 JSON，画布内容的存取与协作有了数据基础；
  • 内置文本、图片滤镜、自由绘制等编辑器常用能力；
  • 面向对象 API 直觉友好，学习曲线平缓。

缺点

  • 约 300 KB 级的体积，对"只画几个图形"的场景是明显的过度引入；
  • 对象数量上千后交互流畅度下降，底层毕竟还是 Canvas 2D 全量重绘；
  • 深度定制要理解框架的对象体系，绕开约定做事的成本不低；
  • 模块化程度有限，难以只按需引入极小子集。

最适合：图形编辑器、在线白板、图片标注工具、贺卡与海报设计器这类"用户操作对象"的产品。

不适合：纯展示型数据图表（那是 ECharts 的领地）、大规模动态场景、对体积极端敏感的页面。

ECharts：声明式的图表语义 ​

优点

  • 声明式配置覆盖绝大多数统计图表，柱状、折线、饼、散点、雷达、地图、关系图开箱即用；
  • 提示框、图例、数据缩放、过渡动画等图表交互全部内置，一行配置可得；
  • 大数据场景有采样、增量渲染等内建优化手段；
  • 中文文档与示例生态是国内同类中最完善的，团队上手阻力最小。

缺点

  • 配置体系庞大，深度定制要在数百个配置项中定位，精通成本高；
  • 语义边界清晰但坚硬：统计图表之外的自由图形表达力不从心；
  • 完整包约 1 MB 级，即便按需引入，对极简页面仍是最大的一块依赖；
  • 高度定制的视觉设计会反复撞上配置项的天花板。

最适合：后台仪表盘与报表、运营大屏的统计图表部分、任何"图表类型已在库的目录里"的需求。

不适合：图形编辑器、3D 场景、高度定制的艺术化可视化、非统计语义的自由绘制。

Three.js：浏览器里的 3D 世界 ​

优点

  • WebGL 最成熟的封装：场景图、几何体、材质、灯光、相机、后期处理成体系；
  • GPU 并行渲染，十万级图元与复杂光照仍有流畅表现；
  • 生态庞大：模型加载器、轨道控制器、后处理通道、大量第三方扩展；
  • 抽象层级的性价比之王：它压掉的复杂度远比任何 2D 库多。

缺点

  • 学习曲线最陡：线性代数、相机投影、光照模型、GPU 概念缺一不可；
  • 文本与 UI 是弱项，3D 场景中的标签往往需要 HTML 浮层或位图字体补齐；
  • 调试困难，着色器问题没有 DevTools 级别的直观工具；
  • 约 600 KB 级的体积与较高的运行时功耗，低端设备需要降级策略。

最适合：3D 产品展示与配置器、数字孪生、大屏 3D 模块、3D 图表与科学可视化。

不适合：常规 2D 图表（用它是杀鸡用牛刀且更贵）、以文本信息为主的页面、对加载体积与功耗敏感的移动端弱设备场景。

矩阵没告诉你的三件事 ​

特性矩阵能量化的都量化了，还有三条隐性差异只在真实使用中浮现：

调试体验。 SVG 的每个图元都能在 DevTools 里被检视、改属性、打断点，调试体验与调试普通网页无异；Canvas 是一个黑盒位图，出问题只能靠日志与二分法；WebGL 的着色器错误则常常只有一行含糊的编译日志。技术越底层，调试工具链越薄。评估工期时，这条差异会直接放大或缩小"疑难问题"的权重。

内容与协作属性。 SVG 是文本：可以进版本库做 diff、可以被设计师用 Figma 导出后手工微调、可以被翻译工具处理；canvas 里的文字画完就是像素，没有任何内容属性可言。需要多人协作维护的图形资产，SVG 有结构性优势——图标库、插画系统这类"资产型"项目几乎都落在 SVG 上，这不是巧合。

问答密度。 ECharts 的中文问答密度在国内技术社区中名列前茅，几乎任何报错都能搜到现成答案；Three.js 的优质内容以英文为主；Canvas 与 SVG 作为标准，MDN 文档即最终答案。团队的英语与检索能力，也是选型变量之一——排障效率在工期紧张时会直接换算成交付风险。

这三件事的共同点是都不出现在任何官方文档的卖点页上，却每天都在真实开发中发生作用。把它们写出来，是提醒选型评估不要只看宣传页与演示站：找团队里真正用过的人聊半小时，收获往往超过读十篇对比文章。

四个容易误读的格子 ​

矩阵里有四行在实际选型中最容易被扫一眼带过，值得单独展开——它们恰好都属于"平时用不上，用上就是一票否决"的类型。

SSR 友好度。 这一行决定你的图形能否在服务端生成。SVG 是纯文本，Node 端拼字符串即可产出完整图形，邮件报表、静态站点、SEO 敏感页面都受益；ECharts 官方提供服务端渲染方案，在无浏览器环境输出 SVG 字符串，正好覆盖"服务端出报表截图"这类需求；三个 Canvas 系方案与 Three.js 都依赖真实绘图环境，服务端只能借助无头浏览器，成本高一档。如果需求包含服务端出图，这一行是一票否决级的。

事件模型。 这一行的差异不会出现在演示页上，只会在交互需求变复杂时显形：SVG 与 Fabric.js 的图元天然可点；ECharts 的事件按"系列与数据项"的语义派发，你拿到的是数据而不是图形，这恰好是图表场景想要的抽象；Canvas 2D 与 Three.js 则要把"哪个图元被点中"自己算出来。交互深度越高的产品，越应该让这一行在决策中占更大权重。

导出能力。 业务上的导出需求分布很集中：报表导出图片（各家都行）、编辑器导出工程文件（Fabric.js 的 JSON 序列化是现成答案）、印刷物料导出矢量（只有 SVG 与 Fabric.js 的 SVG 导出可行）。先问清导出物的消费者是谁——是人看图、是系统存档、还是印刷厂——再回头看这一行，答案会自动浮现。

学习曲线。 注意入门与精通是两段曲线：ECharts 入门极平缓，精通配置体系却很陡；Canvas 2D 入门平缓且没有精通陡坡，代价是深度需求全要自己造；Three.js 从第一天起就是陡坡，但翻过之后的表达力天花板也最高。评估时问的是"团队要走到哪一段"，而不是"第一课难不难"。

用矩阵做排除法：一个实例 ​

需求：运维监控页的实时散点图，5000 个数据点每两秒刷新，hover 任意点查看详情，图表要能导出图片发到值班群。

拿着需求逐行走一遍矩阵：

  1. 渲染模式：5000 点加高频刷新，SVG 节点方案直接排除（量级依据见下一页实测），候选收窄到 Canvas 系；
  2. 事件模型：hover 查看详情是硬需求——Canvas 2D 要自建命中检测与提示浮层，ECharts 的提示框开箱即用，天平明显倒向后者；
  3. 导出能力：两者都能导出位图，打平；
  4. 依赖体积：ECharts 按需引入散点系列与必要组件，体积增量可控；
  5. 学习曲线：团队无 Canvas 经验，ECharts 配置式上手更快；
  6. 结论：ECharts 散点系列，交互用内置 tooltip 与 dataZoom，导出用内置的保存为图片功能，半天交付。

这个推演用时不超过十分钟——这就是矩阵的用法：它不能替你下结论，但能让得出结论的过程变得机械、快速而可靠。注意推演里的每一步都引用了矩阵的具体行，这正是评审时需要的表达：结论可以有争议，但依据必须可追溯。

这个推演还有一个性质值得强调：可重跑。需求变更时——点数从五千涨到五万、临时新增导出 PDF 的要求——只需回到矩阵受影响的行重新评估，其余行的结论原样保留，不必从头再来。把选型依据显性化在这张表里，长期收益会在第二次、第三次变更时持续兑现。

相同点小结 ​

剥开所有差异，五者的共同点依然牢固——这些共同点决定了在一项技术上学到的知识，大部分可以原样带到另一项：

  • 都基于同一套浏览器图形栈，最终都要变成像素合成到屏幕，都要服从帧预算的约束；
  • 都在做数据到视觉通道的映射，映射设计的优劣与技术选型无关，是通用的可视化素养；
  • 都能与 DOM 混排：图形区域交给专门技术，外围的标题、面板、提示永远是普通 HTML，真实项目几乎都是组合架构；
  • 都在持续进化：OffscreenCanvas 正在把绘制移出主线程，WebGPU 已在路上，ECharts 与 Three.js 都在跟进新后端——值得关注，但不要为尚未落地的特性做今天的决策；
  • 都有成熟的框架集成模式：无论 React 还是 Vue，五者都遵循"挂载时初始化进容器引用、卸载时销毁释放"的同一生命周期写法，封装成组件的代码结构高度同构，从一种技术迁移到另一种时外壳几乎不用改。

本质差异一句话 ​

五者的本质差异是"你离像素有多远"：SVG 把像素管理全部交给浏览器，你只描述图形；Canvas 2D 把像素全部交给你，浏览器只提供画笔；Fabric.js 与 ECharts 在 Canvas 之上分别预建了对象模型与图表语义，用自由度换效率；Three.js 则把你带到另一条 GPU 管线上，用编程模型的复杂度换数量级的吞吐。选型就是在这条"离像素远近"的光谱上，为当前需求找到总成本最低的那一点。

这句话还有一层推论值得记住：离像素越远，库替你做的决定越多，出问题时你能干预的余地就越小。选择高抽象层级，等于用"日常效率"预购"极端情况下的无能为力"——成熟的工程师会同时评估这两样，而不是只为前者心动。

小结 ​

本页用一张特性矩阵、五段代码形态与五组优缺点清单完成了横向对比：矩阵回答"某特性谁有谁没有"，代码形态回答"写起来像什么"，优缺点回答"什么场景该用谁"。三个结论值得记住：其一，没有全能技术，每一项优势都标好了价格；其二，体积、运行时性能、开发效率是三本独立的账，不能合并计算；其三，真实项目几乎都是组合架构，技术之间的边界比想象中清晰。下一页性能对比与实测聚焦其中最容易被误读的一本账——运行时性能，用机理分析加可操作的压测组件把"谁更快"讲清楚；再往后开发成本与选型决策把三本账合并成可执行的选型流程。
